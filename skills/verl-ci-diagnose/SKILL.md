# verl CI 排查

将用户提供的失败 CI 链接转化为可追溯的诊断、回归区间和可执行的下一步。默认用中文报告，保留命令、配置键和错误原文。无需让用户重复提供能从仓库、run 日志或本次对话中取得的信息。

## 范围与交付分支

- 输入通常为 GitHub Actions run/job URL；也接受 PR URL、成功 run URL 和已有复现日志。先识别仓库、run、attempt、job/matrix 和用户关注的问题。
- **nightly CI**：完成分析报告和修改意见，并按 [NPU 复现包规范](references/nightly-npu-repro.md) 实际生成复现包与使用说明。不能只给零散命令或表示以后可以生成。
- **PR CI**：完成分析报告、具体修改建议和验证方案后，询问用户下一步，例如本地修改验证、准备 PR，或继续补证。默认在此处交接，不自行修复仓库、推送或提交 PR；如果用户本次或前文已明确授权相应动作，继续执行，不重复询问。
- 按实际 workflow、job 和测试内容分类，不仅看触发事件：PR 事件也可能运行完整 nightly job。一个链接有多种任务时，分别说明范围；只交付与故障相关的 job，注明未覆盖的其他任务。
- 开始前阅读适用的 AGENTS.md。诊断授权包括读取、下载证据、隔离的本地实验及生成报告/复现文件；不自动扩展为重跑远端 CI、改 workflow、发评论或发布 PR。尊重既有授权。

## 1. 建立失败事实

优先使用可用的 GitHub 连接器；能力不足时用 `gh`/GitHub API 获取 Actions 元数据、所有分页的 jobs、完整日志及相关 artifacts。无法访问或日志过期时说明具体缺口，继续利用已有证据；不要把访问失败当成不存在。

记录：

- run/job URL 和 ID、attempt、workflow 路径、事件、分支、起止时间及结论；链接若指定 job，先分析该 job，再检查上游依赖。时间注明时区。
- API 的 head SHA、日志里**实际 checkout SHA/ref**，以及多仓库/子模块的实际版本。PR head、base 和测试 merge commit 要分开，不能把 PR 当前 HEAD 当作历史 run 的代码。
- 首个与故障有因果关系的错误、完整异常链、失败 step、退出码和受影响范围。区分原始错误、Ray/分布式包装异常、后续连锁失败及清理错误。
- 对精度回退同时检查训练是否完成、具体 metric/step、baseline 内容和阈值；不能只看 job 红绿或最终汇总值。

从该 run 对应的 workflow/reusable workflow、action、安装脚本、训练脚本和日志还原**实际执行链**。特别核对最终展开的命令与配置覆盖值，而非只读脚本默认值或当前 main。保存必要的原始证据；摘录须能追溯到 job/step 或本地日志行。

## 2. 选择可比的成功运行

若用户给出成功 run，先核验它是否可比；否则向前查找同 workflow、同 job/matrix 的最近成功运行，必要时继续寻找最后已知成功和最早已知失败。

- 必须确认目标 step 确实执行并通过。跳过、取消、允许失败或根本没跑目标测试，不算成功对照。
- 对照硬件型号与架构、节点/卡数、并行拓扑、模型/数据、训练步数、batch、评估规则和环境。差异过大时寻找更近似的对照；仍不可比则明确限制。
- 检查同 SHA 的重跑结果及附近反例，以区分稳定回归、偶发问题和环境漂移。一次通过不能证明缺陷已消失。
- 不无限遍历历史：找到有用的回归区间或已确认日志不可获得即可转入分析，交代搜索范围与证据缺口。

## 3. 对比代码、运行配置和环境

建立成功/失败差异表，至少覆盖影响本故障的以下维度；未记录的信息写“未知”，不能推定一致。

| 维度 | 需要核对的证据 |
| --- | --- |
| 代码 | 实际 checkout SHA、提交祖先关系、workflow/launcher/业务调用链差异、关联 PR |
| 启动配置 | 展开命令、Hydra 最终覆盖值、随机种子、步数、batch、offload、并行度 |
| 环境 | runner/架构、容器 tag 与 digest、宿主驱动/固件、CANN、Python、torch/torch_npu、vLLM/Ascend、相关依赖 |
| 安装行为 | 安装顺序、索引源、constraints、额外安装和覆盖、editable/VCS 提交及实际导入路径 |
| 输入与判断 | 模型/tokenizer/processor revision、数据来源/预处理/过滤数量、缓存、baseline 文件及校验逻辑 |

只展示与故障有关的依赖和差异，完整清单可存为附件。镜像 tag 相同不证明 digest 相同；包版本相同不证明代码/二进制相同；模型路径、数据数量相同不证明内容相同。日志没有 digest/hash 时不能补造。

对 commit 关系先验证祖先关系：同一线性历史可列出成功到失败间的提交；来自不同 PR merge refs 或分支时，比较双方相对共同祖先的变化及两棵树的差异。注意 GitHub 三点 compare 的方向和范围，不能把它当作两端完整差异。必要时核对关键文件 blob SHA。

将候选提交映射到 PR，阅读实际 diff、相关讨论与已有修复。不要把“时间上最后合入”当作因果证据，也不要假定所有问题都由 verl PR 引入；依赖、输入、缓存、runner 和判定标准变化同样可能是原因。

## 4. 建立归因与验证方案

对每个主要候选说明：PR/commit、相关代码位置、触发机制、支持证据、反例/未解释部分，以及最小区分实验。证据强度使用：

- **已确认**：直接证据或受控实验建立因果链，写清确认的是哪个具体结论。
- **高度怀疑**：调用链与差异吻合，但缺少控制变量验证。
- **待排查**：仅时间相关或关键证据不足。

不要强行选一个 PR；允许多个 PR 交互、环境变化或尚不能归因。优先选择能区分候选的一次实验：同环境切换 good/bad SHA、固定代码切换单一依赖、撤销一个候选变更、或补充最小诊断。选择性回退/cherry-pick 可能依赖其他提交，需交代实验实际改变了什么。需要 NPU 而当前无设备时交付实验入口，不能声称已复现或已验证修复。

修改建议要具体到文件/函数/配置和行为，解释为何能解决症状、潜在影响及测试办法。数值回退不能靠降低 baseline、减少训练步数或换一套数据伪装修复。新增同步、张量读取/哈希或大量日志可能影响时序，作为独立诊断模式标明。

## 5. 报告与下一步

先写结论和置信度，再给支撑证据。报告通常包括：

1. 故障摘要：哪个 job/step、症状、影响与当前判断。
2. 成功/失败对照：链接、attempt、真实 SHA、关键配置和环境差异。
3. 回归区间及候选 PR：证据、反证、尚缺什么；明确哪些内容是推断。
4. 修改建议与验证方案：具体修改点、控制变量、预期结果及风险。
5. 已完成验证与限制：列实际命令和结果，区分静态检查、CPU 检查、NPU 运行；链接本地证据和交付物。
6. nightly：提供复现包、完整使用命令、环境等价性表和结果回传说明。PR CI：给出建议后询问用户选择下一步；已授权的后续工作继续执行。

长报告可保存为 Markdown，与证据/复现包放在本次任务的独立目录，最终回复保留关键结论和可点击文件链接。不要在用户未授权时向 GitHub 发布报告。

如果后续进入 PR 阶段，先遵循当前仓库贡献规范。对 verl，在提出 PR 前完成相关 issue（若存在）及评论检查、按 issue 编号搜索 open PR、按领域关键词搜索 open PR。发现同修复不重复提交；实质不同的方法须按仓库要求说明。PR 说明包含非重复理由、真实测试命令与结果、AI 辅助声明；人类提交者仍需审阅全部改动并运行相关测试。此 skill 不代表人类已经完成这些步骤。
