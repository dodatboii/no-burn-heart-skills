# Nightly CI 的 NPU 复现包

仅在 nightly 分支读取本文件。目标是在用户的 Ascend NPU 机器上，以尽可能少的操作重现**指定失败 job 的完整实际执行流程**，包括环境准备、数据预处理、训练和原有 baseline 检查。复现相同流程不保证非确定性故障每次出现。

## 先明确等价性

以失败 run 的实际 checkout、workflow 和完整日志为输入，而不是拿最新 main 或“类似的训练示例”替代。将已取得的脚本和配置固化进包，或在运行时按不可变 SHA 获取并校验。

逐项记录“CI 观测值 / 复现值 / 来源 / 是否一致或未知”：

- NPU 型号、CPU 架构、节点数、每节点卡数和进程/并行拓扑。
- 宿主驱动、固件、CANN、容器镜像 digest、设备与库挂载、网络、共享内存、ulimit 和工作目录。
- Python、torch/torch_npu、推理后端、其他相关包的版本、VCS SHA、安装顺序、安装源与约束。
- 仓库 SHA、模型/processor/tokenizer revision、模型文件、数据和 baseline 的来源、内容 hash 与目录映射。
- 预处理、训练、评估和检查的原始命令、有效环境变量、最终配置、种子、步数及退出条件。

区分源 run 已知值、用户宿主前提和未知项。若历史镜像 digest、依赖解析结果或模型/数据内容未留存，明确“历史环境不能完全核验”，仍交付最接近的可运行方案和差异清单。不能因包已生成就称为已验证的完全等价复现。

缺少硬件信息时先从 runner 标签和日志提取要求，并制作预检；只有信息确实阻塞实现时才询问用户。不要把某次事故的具体镜像、卡数、模型、路径或步数固化成所有任务的默认值。

## 实际文件交付

在独立输出目录生成可解压使用的目录和压缩包。可以按任务调整文件划分，但应包含以下职责：

```text
verl-nightly-repro-<run>-<job>/
  README.md             # 中文说明、精确运行命令、判定方式和环境差异
  manifest.json         # run/attempt/job、SHA、镜像、输入、依赖、来源和未知项
  env.example           # 用户需要设置的路径/地址/凭据变量名及合理默认值
  preflight.sh          # 宿主和容器前提检查，明确缺少什么
  run_host.sh           # 设备/缓存/日志挂载、容器创建及失败退出码传播
  run_container.sh      # CI 安装/预处理/训练/检查的同序执行入口
  collect_env.sh        # 有边界、脱敏的版本和环境指纹采集
  ci/                   # 固定版本的 workflow、脚本、配置或源代码快照
  patches/              # 仅在存在候选修复时提供，并注明适用 SHA
  SHA256SUMS            # 包内交付文件校验
```

不要求把巨大的模型、镜像和数据直接塞入压缩包。提供固定 revision 的准备/下载入口、缓存挂载和完整前提；离线条件只有用户要求时才增加。不能只有文件名列表、未实现脚本或需要用户拼接的散乱片段。秘密不写入包、日志或 manifest，按变量名引用并说明必要的最小权限。

## 运行行为

- 默认入口是**失败版本的原始完整运行**，不得默认带修复 patch、降卡、减步数、缩小 batch、放宽阈值或跳过 checker。只有一个 mode 时也要清楚说明。
- 有候选修复时可增加 `patched` 模式，保留原始模式。若增加 `good` 对照，明确是历史成功环境复现，还是固定环境只切换代码的控制变量实验。两者含义不同。
- 缩小规模的 `smoke` 只能是显式的独立模式，标为环境检查，不能宣称等价 nightly 或用它验证精度回归。
- 各模式使用独立 checkout/output，校验实际 SHA，避免覆盖用户代码；patch 不匹配立即报错，不能静默跳过或重复叠加。
- 固定镜像 digest 和可取得的依赖/模型/data revision。历史信息缺失时显示差异，禁止默默改用 latest 或安装“最新版”。如果 CI 使用浮动安装，记录原流程以及用于固定历史版本的调整。
- 优先复用原容器内 Python 环境和 CI 安装行为。需要新建本地 Python 环境时遵循仓库的 uv 规范；不能为迎合当前开发环境而无声改变历史 CI 的解释器、安装器或依赖解析语义。
- 将 CI 中不同 step 的工作目录、环境持久化、服务启动和依赖顺序正确映射到脚本。不得直接把未展开的 GitHub Actions 表达式放入 shell。
- 预检校验架构、可见 NPU 数、驱动/容器兼容前提、空间、共享内存、输入文件和必要工具。宿主前提不符时给具体修正办法，不能自动安装驱动或修改宿主系统。
- 按源 job 的设备/库要求构造容器参数，说明所需权限。只停止本包创建的容器/进程，不做全局 `pkill`、全局 `ray stop` 或清空用户缓存。
- 使用可靠的失败传播；经 `tee` 保存日志时保留训练/检查真实退出码。不得用 `|| true` 吞掉训练、安装或 baseline checker 的失败。
- 每次运行单独保存完整 stdout/stderr、最终配置、阶段退出码、环境指纹、评估值与 baseline 比较结果。失败时也应保留可采集的诊断。
- 环境指纹默认使用白名单字段、版本/路径/元数据。大文件 hash 及张量内容采集显式选择，避免打印整个环境变量或引入未说明的时序扰动。
- 多节点任务需有实际可执行的各节点启动顺序、主节点地址/端口、rank、通信和日志收集说明。单机脚本不能冒充多节点复现。

## 使用说明必须回答

1. 这份包对应哪个 run/attempt/job，覆盖哪些步骤？
2. 需要什么机器、节点/卡数、磁盘和宿主软件？哪些由镜像提供？
3. 如何解压、配置模型/数据/缓存路径、准备输入、预检和一条命令启动完整复现？默认值足够时不要强迫编辑配置。
4. 如何读取真实失败退出码、训练指标和原始 baseline 检查结果？报错可能在哪个阶段出现？
5. 如何显式选择原始、候选修复或成功对照，差别是什么？
6. 已验证到什么程度，尚有哪些环境差异或待验证假设？
7. 运行结束后应回传哪些日志/配置/指纹，如何只清理本次资源？

## 交付前验证

执行与产物匹配的检查：`bash -n`、manifest/配置可解析、引用文件齐全、入口帮助或 dry-run、归档解压后相对路径可用、文件校验及可执行权限。若有多模式/复杂退出码处理，用不依赖 NPU 的小型执行测试验证模式隔离和失败传播；不要执行真实下载或全量训练来测试帮助入口。

核对复现脚本与 CI 原始流程的对应关系，重点是安装顺序、卡数、训练步数、batch、baseline 下载及 checker 参数。检查默认路径没有偷偷应用修复。

没有 NPU 时报告“静态/本地检查已通过，NPU 端待执行”，列出实际检查结果。若能访问用户授权的 NPU，运行所需验证并记录结果。最终回复链接目录、压缩包、README 和报告，给出能直接复制的启动命令以及明确的宿主前提。
